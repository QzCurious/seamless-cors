# Module, adapter, and platform boundaries

The Managed PAC module and seam decisions below are superseded by [ADR-0012](./0012-dynamic-system-pac-lifecycle.md). The separate Network Service external-system module remains in force and is now hidden behind the System PAC module.

Managed PAC, UserCA, File Observation, Upstream List, PAC Routing, CORS, HTTPS Facade, and Proxy are separate modules that own their semantic types, concrete errors, mutation serialization, and internal resources. HTTPS Facade owns one projection of Origin Selectors into browser HTTPS origin to HTTP upstream mappings for both PAC Routing and Proxy, while CORS owns the product's fixed Local Preflight Answer and Response Repair policy. Proxy owns goproxy transport mechanics and directly adapts CORS, HTTPS Facade, and optional UserCA Signing Material; there is no configurable CORS seam or separate TLS/CA wrapper module.

A feature module may depend on a cohesive external-system module when that module exposes platform-neutral facts and mutations without adopting feature policy. UserCA therefore owns seamless-cors certificate identity and lifecycle policy while Trust Store owns current-user operating-system root-store listing, addition, removal, and platform error interpretation. Managed PAC owns marker recognition, its control lifetime and fixed service set, fresh-observation policy, observation-issue classification, ownership and drift classification, serial Set attempts, private Service-PAC State, purpose-built reports, and cleanup verification while Network Service separately owns current-user operating-system service discovery, per-service PAC observation and mutation, platform representation normalization, and contextual platform errors. Managed PAC does not classify mutation failure causes beyond preserving their diagnostics.

Managed PAC exposes two capability seams backed by one implementation: Activation begins an activation-scoped Control and returns a Managed PAC Activation Assessment, while Footprint performs ownerless active-state inspection and cleanup. Control delivers the current PAC Endpoint, returns fresh purpose-built Control State, and closes its lifetime. Gateway composition may hold both capabilities, but each workflow depends on the narrow capability it uses. Gateway never receives raw Service-PAC State, reconstructs manageability, compares PAC URLs, or reclassifies Managed PAC warnings; it combines the feature-owned Routes Current Endpoint fact with PAC Endpoint and Proxy serving facts to derive Traffic Routing Ready. No feature module initiates another feature's lifecycle; Gateway alone coordinates cross-feature state and ordering without a global lifecycle mutex, and callers use feature-owned values unless Gateway deliberately exposes a different semantic shape. Gateway's private UserCA seam is one such deliberate shape: its production adapter translates UserCA-observed current state into the facts needed for HTTPS coordination, so Gateway adapters and tests cannot manufacture UserCA-owned current truth.

Independently composed Inbound Adapters live under `internal/inbound`, depend inward on the modules they drive, and expose a small interface to the composition root. Production packages outside `cmd` do not import them; the CLI exposes `NewCommand`, which constructs its Cobra command tree, while the private authenticated HTTP Gateway Router remains inside the Gateway Module. CLI command definitions own argument validation, terminal streams, signal handling, and presentation of module results; the composition root executes the tree and selects the process exit status.

A Gateway Distribution is supported only when every required OS-managed feature has a complete build-tag-selected adapter and compile-time interface assertion. Missing implementations fail target compilation rather than becoming runtime no-ops or capability gates; production adapters remain pure Go and cross-compilable, while executable build and release configuration defines the changing OS and architecture matrix.

There is no generic platform package or dependency bundle. Small command helpers remain local to their feature; a separate deep OS-mechanics module is justified only when it hides substantial platform variation behind one cohesive interface and leaves product interpretation with its caller.
